<objective>
Stand up the backend service: Express on TypeScript, a config module that validates the Anthropic API key once at startup and fails fast, a health endpoint, and a Dockerfile. No Anthropic calls yet — Phase 2 adds the routes.
</objective>

<context>
The artifact had no credential handling whatsoever: all three `fetch` calls sent only `Content-Type`, and worked solely because the Claude.ai host injected auth. That is the single thing this backend exists to replace.

Deployment shape is **single-tenant self-hosting**: one deployer, one container, their own key, on their own trusted machine. This was resolved in `docs/MIGRATION-PLAN.md`, which also records why two alternatives were rejected (a baked-in key makes the original developer pay for everyone; paste-per-session BYOK adds friction without buying protection against anything realistic for a deployer on their own box). Do not re-litigate it.

R2 is the security requirement and it is specific: the key must never appear in the frontend bundle, in any log line, in an error response, or in a stack trace. `docs/MIGRATION-PLAN.md` calls this "a code-review checklist item, not just a storage-layer concern."

Read `.planning/phases/01-foundation-contract/01-CONTEXT.md` first.
</context>

<task id="2">
<action>
Write `backend/src/config.ts` as the single place environment is read:
- Read `process.env.ANTHROPIC_API_KEY` **once at module load**
- If absent or empty, throw with a message naming the variable, pointing at `.env.example`, and stating that `cp .env.example .env` then adding a key fixes it. The process must exit non-zero at startup — not three calls deep into gameplay.
- Export the key only as the value the Anthropic client consumes. Do not export it on a broadly-shared config object that is liable to be logged wholesale.
- Also centralize `PORT` and the model IDs here (Phase 2 consumes the models): `claude-sonnet-5` for unique-skill; `claude-opus-5` for world-engine and intro-scene. Model ID strings are complete as-is — never append a date suffix.

Add a guard that makes accidental key exposure hard: a redaction helper used by the error handler, and a `toJSON`/`inspect` on any config object that would otherwise serialize the key.
</action>
<verify>
Run the server with `ANTHROPIC_API_KEY` unset: it must exit non-zero and print the actionable message. Run with a dummy value: it must start. Then `grep -ri 'sk-ant' backend/src/ || echo "no literal keys"` and confirm no key literal is committed.
</verify>
<done>The backend fails fast and legibly without a key, starts with one, and the key is not exported in a shape that invites accidental logging.</done>
</task>

<task id="3">
<action>
Add `GET /api/health` returning `{status: "ok"}` with a 200, plus a central Express error handler that returns structured JSON errors (`{error: {message, code}}`) and **never** includes the API key, raw provider error bodies, or stack traces in the response body. Log the full error server-side; return the sanitized shape to the client.

Write `backend/Dockerfile`: a Node 22 base, dependency install honoring the workspace layout, TypeScript build, and a non-root runtime user. Do not bake any secret into the image — the key arrives as an environment variable at run time.
</action>
<verify>
`curl -s localhost:3001/api/health` returns `{"status":"ok"}`. Trigger a deliberate error on a throwaway route and confirm the response body carries no stack trace and no key. `docker build -f backend/Dockerfile .` succeeds. `docker history` on the built image shows no `ANTHROPIC_API_KEY` value baked in.
</verify>
<done>Health check responds, errors are sanitized before they reach the client, and the image builds without embedding a secret.</done>
</task>
