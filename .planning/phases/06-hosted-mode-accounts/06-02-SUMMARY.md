## Decisions and facts
**Better Auth version and CLI (critique 3).**
- `better-auth` is pinned at **1.7.6** (`"better-auth": "1.7.6"`).
- The CLI is the npm package **`auth`**, not `@better-auth/cli`, for three reasons:
  - the installed library tells users to run `npx auth secret` (`node_modules/better-auth/dist/context/create-context.mjs:44`);
  - `npm view auth@1.7.6` gives `description = 'The CLI for Better Auth'`, the better-auth repository, bin `auth`/`better-auth`, and depends on `better-auth: '1.7.6'` exactly;
  - `@better-auth/cli`'s latest version is 1.4.21, a stale line.
- The better-auth README names no CLI, and `better-auth`'s own `package.json` has no `bin`.
- The exact command, run in a scratch dir against an empty PG16 database, with a throwaway `auth.ts` (magicLink plus the google and discord providers, `telemetry: { enabled: false }`, fake values):
  `npx -y auth@1.7.6 generate --config ./auth.ts --output ./001.sql --yes`
- Telemetry is opt-in by default anyway (`@better-auth/telemetry/dist/node.mjs:449`).
- The magic link and the providers add no columns in 1.7.6. The user id type is `text`, so 002 uses `text` as the spec says.

**node-pg-migrate 9.0.0 facts (installed source, `node_modules/node-pg-migrate/`):**
| Fact | Where |
|---|---|
| ESM: `"type": "module"`, `engines.node >=20.11.0`; `.` → `dist/bundle/index.js` | `package.json` |
| `runner` is a named export | `dist/bundle/index.js:3614`; `dist/legacy/index.js:8-9` |
| Advisory lock by default: `if (!options.noLock) await lock(...)`; `pg_try_advisory_lock(7241865325823964)`, fail mode by default (throws "Another migration is already running") | `dist/legacy/runner.js:134`, `:39-46`, `:12` |
| `.sql` files go to the legacy SQL loader | `dist/legacy/migrationLoader.js` `getDefaultStrategies` (`extensions: [".sql"]` → `legacySql`) |
| Markers: regex `^\s*--[\s-]*${direction}\s+migration` (flags `im`); the up section is everything from `-- Up Migration` to `-- Down Migration`; no down marker means `down: false` | `dist/legacy/sqlMigration.js:3-20` |
| `schema` option: `CREATE SCHEMA IF NOT EXISTS` (with `createSchema`), then `SET search_path`; the migrations table goes in the first schema | `runner.js:135-139`; `utils/getMigrationTableSchema.js` |
| Each migration is wrapped in `BEGIN;`/`COMMIT;` unless `singleTransaction` is set | `dist/legacy/migration.js:139-146` |
| A migration's name is the file name without its extension | `migration.js:106` |
| The "could not connect" log line `util.inspect`s the driver error, which is why `migrate.ts` redacts its `log` | `dist/legacy/db.js` (`createConnection`) |

Other decisions:
1. **`assertNoPendingMigrations` reads the table rather than doing a dry-run `runner()`.** A dry run still takes the advisory lock and runs `CREATE TABLE pgmigrations` (`runner.js:134`, `:141`, `:66`). The read-only check uses node-pg-migrate's own `getMigrationFilePaths` (the public subpath `node-pg-migrate/migration`, `dist/legacy/migration.js:168`), so the ignore rule and the sort are identical.
2. **`createPool` is `async`**, because `pg` is dynamically imported. It attaches `pool.on('error')` with a redacted log, since an unhandled idle-client error would crash the process with raw text.
3. **Redacted errors are new `Error`s** that carry only the redacted message and the driver's `code`, never `cause`, which `util.inspect` would print in full.
4. **`migrate.ts` exports `runMigrations()`**, and `withTestDb` uses it, so the tests run the production migrate path.
5. **Not wired into `main()` here.** `server.ts` is not in this plan's files. The exit-with-`npm run migrate` behaviour is `db.ts` throwing `PENDING_MIGRATIONS_MESSAGE`; the boot wiring (`createPool` → `assertNoPendingMigrations` → exit 1) is **06-04's**, when the hosted branch lands.
6. **`test-db.sh` specifics.** The cluster is at `/tmp/soulbound-test-db` (override with `SOULBOUND_TEST_PGDIR`). It uses `--auth=trust` on 127.0.0.1 only, and its socket lives in the cluster directory (the system socket dir may not exist).
