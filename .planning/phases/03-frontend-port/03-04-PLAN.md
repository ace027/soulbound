<context>
Read `.planning/phases/03-frontend-port/03-CONTEXT.md` first — especially "Behavior tuned by feel".

Port target: legacy `handleAction` lines **925-1021**, as a pure function of
`(gameState, action, worldVoiceResult)` returning `{ state, logEntry, newSkillIds }`. Strip every
`set*` call; they stay in `App.tsx` (plan 03-09).

**The range is 925-1021, not 925-1008.** An earlier draft said 1008, which ends at the `sceneEvent`
block — but `newLogEntry` is built at **1014-1021** from `rewrites` and `subAbilityUnlock`, both
locals of the pure region. Returning `logEntry` while porting only to 1008 is impossible; critique
caught the contradiction. `setGameState`/`setNewSkillIds`/`setTimeout` (1010-1012) stay in 03-09.

**Return `newSkillIds` as a `Set<string>`, typed explicitly.** Legacy builds `new Set()` (929) and
feeds `useState(new Set())` (797), which `SkillCard` reads via `.has(...)`. A name like
`newSkillNames` reads as an array; if a `string[]` reaches a `Set`-typed state the new-skill glow
silently stops working at runtime, not compile time.

**Import `MAX_NARRATIVE_NOTES` from `@soulbound/shared`** (already exported at line 99) — do not
define a local 40.

**Method: port statement-for-statement first, write tests against that, and only then consider
tidying.** The ordering in this function is load-bearing and was tuned by feel:

- Evolutions are applied **after** new skills are pushed onto the same `updatedSkills` array — so a
  skill granted this turn can be evolved this turn. Reordering silently changes behavior.
- The sub-ability lookup `find(s => s.tier === "Unique")` (line 976) runs **after** a Soul Rewrite
  may have renamed that skill, so the unlock attaches to the *new* name.
- Soul Rewrite fires only when `old_tier === "Unique" && new_tier === "Unique"` (line 956). Dropping
  the `old_tier` half makes a Unique→Ultimate evolution wrongly wipe mastery, sub-abilities and notes.
- `usage_notes` accumulate on the **Unique skill only** (lines 934-936).
- Narrative notes cap is an inline `.slice(-40)` (line 994). Keep the behaviour, importing
  `MAX_NARRATIVE_NOTES` from `@soulbound/shared` rather than defining a second 40.
- **`mastery: ns.mastery || 5` (line 946) is a falsy-coalesce, not a nullish one.** A granted skill
  sent with `mastery: 0` becomes **5**. Writing `?? 5` is the most natural thing a careful TS porter
  does and it changes the game-balance surface. Same shape at `sceneEvent.location ||
  newState.location` (1006-1007).
- **Non-Unique `usage_notes` is written as `undefined` on purpose** (936-937). Under `strict: true` a
  porter naturally writes `?? []`, changing the saved shape.
- `const changed = new Set()` (929) is assigned at 938 and never read. It is dead. Port it with a
  comment so nobody "fixes" it into something.

**Do not add a client-side threshold guard.** The 25/60/100 rule is model-side
(`WORLD_SYSTEM_PROMPT` lines 40, 55, 93, 139). A client check duplicating it would silently swallow
legitimate unlocks when a mastery jump overshoots a threshold. The client's job is: dedupe, attach to
the Unique skill, render.

**`Math.random()` stays out.** Legacy line 877's intrinsic roll belongs to the questionnaire flow in
`App.tsx`, not here — a pure function that calls `Math.random()` is not pure and not testable.
</context>
