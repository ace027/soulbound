</objective>

<context>
Read `.planning/phases/03-frontend-port/03-CONTEXT.md` first.

`frontend/package.json` currently has scripts `dev`, `build`, `preview` and **no test script and no
vitest dependency** — verified. `backend/` already runs vitest, and root `npm test` is
`npm run test --workspaces --if-present`, so adding a `test` script here is enough for the root
command to pick it up.

Copy `backend/vitest.config.ts`'s shape rather than inventing one: plan 02-02 already solved the

modules are pure and would run under `node`, but one config for the workspace is simpler than two.
</context>

<tasks>

<task id="1">
<action>
Add `vitest`, `jsdom`, `@testing-library/react` and `@testing-library/jest-dom` to
`frontend/package.json` devDependencies, and a `"test": "vitest run"` script. Match the vitest major
version `backend/package.json` uses.

**Create `frontend/src/test/setup.ts`** and register it via `setupFiles` in `frontend/vitest.config.ts`:
- `import '@testing-library/jest-dom/vitest'` — installing the package is NOT enough; without this
  every `toBeInTheDocument()` in waves 2-4 is an unregistered matcher.
- `Element.prototype.scrollIntoView = vi.fn()` — **jsdom does not implement it.** Legacy line 812
  calls it in an effect keyed on `[log]`, with the ref at 738 inside `WorldLog`. Once the simulation
  screen renders the ref is non-null, so the optional chain does not save you: it throws on mount and
  on every log change, and would detonate in wave 4 on this phase's most important test.

Add `"types": ["vite/client", "@testing-library/jest-dom"]` to `frontend/tsconfig.json`.

If you exclude test files from the build, use `"**/__tests__/**"` — **not** `"src/__tests__/**"`.
This phase puts tests in `src/lib/__tests__/`, `src/game/__tests__/`, `src/hooks/__tests__/`,
`src/components/__tests__/` and `src/screens/__tests__/`; the narrower glob matches none of them.
</action>
<verify>
`npm install` from the repo root succeeds. `npm test -w @soulbound/frontend` runs. `npm run build -w
@soulbound/frontend` still passes. Paste all three.
</verify>
<done>Harness installed with jest-dom registered and scrollIntoView stubbed.</done>
</task>

<task id="2">
<action>
Write `frontend/src/__tests__/harness.test.ts` proving the harness runs **what waves 2-4 actually use**,
not a trivial render:
1. a component rendered via RTL asserted with **`expect(...).toBeInTheDocument()`** — the jest-dom
   matcher, not `toBeTruthy()`. A `toBeTruthy()` assertion passes whether or not jest-dom was ever
   registered, which is exactly how a broken harness ships green.
2. a component whose `useEffect` calls `ref.current.scrollIntoView(...)` renders **without throwing**.
3. one trivial truth assertion.
</action>

- invert the trivial assertion → test 3 must fail

A harness observed only passing is not evidence. Phase 2 shipped a suite that passed with its HTTP
routes unregistered.
</verify>
